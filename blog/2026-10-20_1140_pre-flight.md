# Pre-flight notes, 2026-10-20 11:40 UTC

Follow-up to the earlier handoff post. Nothing here has run on a phone yet.

## About the test map
The grey plan in the result plots is the simulator's hand-written `home_plan()` (`sim/floorplan.py`), a 10 x 8 m flat with a central hall. It is
generic test data, not a real place. It may resemble a layout from other coursework by coincidence; I can't verify either way. Swap it with
`--plan random` or add your own flat's layout if that matters. Nothing in the solver depends on it.

## How good is it in simulation?
Modest. Hall wall found well; other walls often ~1 m off or tilted; outer walls essentially invisible to RSS. Levers that moved wall F1 in the sweeps:
more stops (60 stops: 0.61 vs 0.52), faster scans (2 s: 0.61), more APs inside the flat. Algorithm ideas with uncertain payoff: joint
trajectory + wall refinement, annealed search over wall sets, post-fit axis snapping.

## New: `solver check`
`uv run solver check --session data/<name>` prints OK/WARN/FAIL for scan rate, IMU rates, steps detected, BSSIDs heard, marker revisits and RTT
availability. Run it right after each walk; fix any FAIL and re-walk before solving. Documented in `docs/survey-guide.md`.

## Before the first real walk
1. 60-second test recording: check `meta.json` (`scan.median_period_s` << 20, `sensors.acc.achieved_hz` ~ 50), then `solver check`.
2. Calibrate step length (10 m, count steps) and pass `--step-length`.
3. Then the full 5-10 min walk with loops and revisits.

## Biggest open risk
The Android scan/sensor/service/UI glue compiles and its pure logic has unit tests, but it has never run on hardware. If it misbehaves, grab
logcat and `meta.json`.
